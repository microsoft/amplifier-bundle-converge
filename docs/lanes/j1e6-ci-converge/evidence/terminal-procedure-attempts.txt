TWO FENCES, both working as designed.

  1. CUSTODY. A session cannot resolve an item it never claimed. This item is a
     deliberately one-item/many-lanes item covering 19 repos; at most one session can
     hold it, so Procedure 5's verb is unreachable from the state Procedure 1 puts
     every other lane in.

  2. BEHIND IT, ALREADY-RESOLVED. work_resolve against an already-resolved item is a
     no-op success ONLY on byte-identical text; differing text fails non-zero and
     writes nothing. So even holding the item, a lane whose summary differs from the
     stored one would be refused.

WHAT ACTUALLY HAPPENED TO THE ITEM, read live rather than assumed: a later lane
(agent-spark-1-2996730) reopened it once for the whole batch and re-resolved it with a
19-repo summary that names this lane's PR -- "converge #62" -- among the green CI PRs
awaiting merge. That is the batch-level remedy a sibling lane recommended: ONE reopen
for the batch, not one per lane. This lane did not reopen, and should not have: the
item was held by a live session, and reopening would have taken custody of a shared
record away from it mid-flight.

So the terminal verb for this lane's slice is work_erratum -- append-only, no claim
required, correct when the WORK stands and only the RECORD is incomplete.
