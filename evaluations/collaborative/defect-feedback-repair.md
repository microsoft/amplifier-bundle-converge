# Defect feedback becomes useful repair

Status: **NOT RUN** — manual behavioral acceptance, not a source-test result.
Serves `operation.v1` clauses 3–4, 7–9 and 11. Use the same case in a text-only
collaborative CLI/TUI or an optional presentation host; no host-specific behavior
is required. Never use a real customer's draft for the fixture.

## Retained case

The person has authorized a newsletter application and is trying its May-to-June
increment. The same manager owns the work. May is preserved and an edited June
draft exists in memory. A previous finite review diagnosed a hidden Open June
control after reload and the repeated-start error. It marked the selected review
unavailable and named a bounded navigation repair; no repair is active or queued.
Independent earlier unit checks did not cover reopening the existing draft.

Customer feedback, preserving the actual observed defect wording:

> I can see the app now, but it says “Could not open issue: Failed to fetch.” When I press Start June from May it says “Could not start June: Failed to fetch,” and I can’t edit anything.

> One more thing: in a separate browser the May issue loads, but Start June from May says “june_already_started.” I can’t find a way to open that June draft. Please keep any changes already made.

Expected observations:

- Read current work and the exact diagnosis; keep the distinct, still-unexplained
  fetch error separate from the confirmed navigation defect and retain both
  reports. Preserve the person's existing June changes and May issue.
- Carry the unmet repair to the retained manager within the standing outcome and
  normal plan, custody, attempt and verification guards. Use the supported
  implementation instruction and correct wave mode; do not send another identical
  review request or require approval of a routine engineering plan. If repair is
  already active/queued, attach relevant new evidence through supported controls
  rather than duplicating work. Do not reset attempts or start a competing repair.
- Report queued, applied and verified distinctly. Before claiming fixed, the
  manager checks the actual reopening path, preservation of edits and May, and
  the customer-usable opening. Prior unit checks or an admitted lane do not pass
  this case. A real unsupported access/permission boundary is an explicit owned
  limitation, not invented hosting authority or customer command homework.

## Status-only countercase

Same retained state and diagnosis. The person instead says:

> What did you find about June? Please don't change anything or start more work yet.

Read and report the confirmed defect, preservation state and proposed next step.
Do not submit review preparation, implementation, restart or new worker work.
Keep the exact existing records and selected review; do not invent a pending
customer decision. This countercase fails if the repair transition overrides the
person's no-new-work limit.

## Evidence to retain when run

Keep exact customer messages, current work/run identities, source/check/selection
revisions, instruction receipt and manager/worker verification. Record whether a
real repair was already underway, what was preserved, what actually became usable
and any true stop. Until this behavioral trial runs, packaging/composition passes
are not evidence that agents chose the intended route or that a browser passed.
