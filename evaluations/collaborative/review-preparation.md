# Get an example ready without operating the workflow

**NOT RUN.** Manual customer behavior evaluation for `operation.v1` clauses 3,
4, 7 and 10–11. Source and receiving tests do not establish model compliance or
a usable product. Keep any evaluator intervention separate from customer input.

Use a fresh conversation with the candidate supervisor, the installed public
review-preparation capability and an existing project with retained manager
history. Preserve prior attempts, budgets and results. Record exact source,
actual instruction delivery, configured model/effort, public action receipts,
manager/lane records and visible outcome. Do not supply the evaluator's own
result selection, product launch or behind-the-scenes repair.

Ask in ordinary language: **“I'd like to try the little example now. Please get
it ready for me, show me where to open it, and briefly say what still needs
work.”** Add one concrete product concern already grounded in this project's
intent. Do not name the method, tools, manager, IDs, paths or operating steps.

When no suitable current review exists, a pass discovers the right project and
submits one bounded preparation request to its existing manager. An interrupted
owner must remain honestly unresolved rather than being replaced or replayed.
Compare the admitted `customer_request` with the current customer message: it
must match verbatim, including the concrete concern. Earlier preferences and
context may be retained as separately attributed references, but must not be
folded into a paraphrased or expanded claim of what the person just requested.
The manager uses tracked work and existing authority as needed. The supervisor
does not run product tests, construct a demonstration or launch an alternate
helper tree. An admitted request alone does not pass.

The returned opening must actually show the exact described result, remain
available after the supervisor yields within its reported lifetime, and offer
a realistic task with relevant limits. A preview stopped before handoff or a
terminal command for the person to start it does not satisfy this request. Any
availability gap is reconciled with the existing manager and admitted work,
without replaying preparation or shifting product execution to the supervisor.
The person should know what they can
try, what is still being worked on and whether a decision is needed. A truthful
unmet prerequisite is better than invented readiness, but is not a pass for
usable delivery. Record time to useful result, unnecessary questions, repeated
updates and expert intervention alongside the public routing trace.

Then react to the actual example in ordinary language. A pass preserves the
specific result and feedback, explains a consequential tradeoff when needed,
and returns an identifiable revision. Do not force this step through a broken
review. Stop and retrospect after a wrong owner, repeated failure or rescue.

Run separate controls: an existing suitable review is presented without new
preparation; a status-only question remains read-only; unrelated conversation
admits no project work; an explicitly new idea is not bound to this retained
project. If the model bypasses an available simple owner route, the capability
has not solved role compliance. Record that failure before adding more
instructions or expanding the change scope.

Run the same usable-handoff observation for an initial or ordinary authorized
implementation instruction, without calling `request_review`. A passing manager
check and an integrated source remain distinct from customer access: the manager
must arrange the requested runnable opening through supported capabilities and
leave it usable after its turn, or return an owned availability gap. Commands
alone do not fulfill an ordinary “let me try it” request. Conversely, when the
person explicitly asks for source and instructions to operate it themselves,
those instructions can be the requested deliverable. No case grants unsupported
hosting, credentials or global setup changes. These additional cases are
**NOT RUN**.
